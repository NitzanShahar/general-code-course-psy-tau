סיכום, vibe coding והכנה לבחינה

השבוע האחרון של הקורס מוקדש לשני דברים: מבט קדימה, ומבט אחורה.

מבט קדימה — vibe coding. בעבודה האמיתית שלכם במחקר תשתמשו בכלי בינה מלאכותית שכותבים קוד. עכשיו, כשאתם יודעים לקרוא ולכתוב קוד בעצמכם, אפשר ללמוד לעבוד איתם נכון: לנסח הנחיה טובה, לבדוק את הקוד שהמודל כתב, לעבוד עם Git כרשת ביטחון, ולשמור על פרטיות הנבדקים. מי שרוצה להעמיק יכול גם ללמוד איך פונים למודל שפה מתוך קוד (API).

מבט אחורה — חזרה לבחינה. הבחינה סגורה, בלי מחשב ובלי AI: היא בודקת „קרוא וכתוב״ של קוד בסיסי. בפגישה האחרונה נעבור על שאלות לדוגמה, ומומלץ לתרגל קריאה וכתיבה של קוד על דף.

קוד 6.1מה זה vibe coding

הנחיה למתרגל AI

בשיעור זה ארצה להבין מה זה vibe coding, מה הוא נותן ומה המחיר שלו. אני כבר יודע/ת לקרוא ולכתוב קוד בסיסי ב-R ובפייתון, לעבוד בטרמינל (Git Bash) ולעבוד עם Git ו-GitHub. אני רוצה הסבר מדויק ותמציתי.
1. הסבר מה זה vibe coding: לתאר במילים, בשפה רגילה, מה אני רוצה שהקוד יעשה, ולתת לכלי בינה מלאכותית לכתוב את הקוד. ספר שהמונח נטבע בתחילת 2025 בידי החוקר אנדריי קרפתי, שתיאר כתיבה "לפי התחושה" בלי לקרוא את הקוד בכלל — ושבמחקר נעשה את ההפך: נשתמש בכלי, אבל נקרא כל שורה.
2. הסבר את היתרונות: מהירות, עזרה במשימות שגרתיות (קריאת קבצים, ניקוי נתונים, גרפים), והיכרות עם פונקציות שלא הכרתי.
3. הסבר את המחיר, עם דוגמאות ממחקר בפסיכולוגיה: קוד שרץ בלי שום שגיאה אבל מחשב דבר לא נכון — מוחק נבדקים בשקט, מטפל לא נכון בערכים חסרים, או מחשב ממוצע על העמודה הלא נכונה. תוצאה שגויה כזו יכולה להגיע עד למאמר.
4. הסבר את עקרון Human-in-the-Loop ("אדם בתוך הלולאה"): הבינה המלאכותית היא עוזרת, והאדם הוא האחראי. כל שינוי שהכלי מציע — קוראים, מבינים, ורק אז מאשרים או דוחים. לעולם לא מאשרים הכול בלחיצה אחת (Accept All) בלי לקרוא. מי שחותם/ת על המחקר אחראי/ת לכל שורת קוד, גם אם מודל כתב אותה. ולכן חייבים לדעת לקרוא קוד — וזו בדיוק הסיבה שלמדנו קודם לכתוב בעצמנו.
5. הסבר את כלל הקורס: המטלות נכתבות בלי בינה מלאכותית, והבחינה סגורה, בלי מחשב. הפרק הזה מלמד שימוש אחראי לעבודה המחקרית, לצד הקורס ואחריו.
6. הצג את מפת הפרק במשפט אחד לכל נושא: איך מודל "כותב" קוד; מצ'אט לסוכן; מפרט וצעדים קטנים; הנחיות קבועות לפרויקט; שגיאות ושורש הבעיה; הזיות ובדיקה; Git כרשת ביטחון; API ו-JSON; סודות; פרטיות ושקיפות.
7. סכם בארבע שורות את מה שהוסבר, וכתוב ששלב הלימוד הסתיים.
הצג את השלבים האלו אחד אחד לפי הסדר. אחרי כל שלב עצור וחכה שאכתוב „המשך״. בשיעור הזה רק מסבירים: אל תשאל אותי שאלות ואל תיתן לי תרגילים — התרגול נמצא ביחידה נפרדת.

קוד 6.2איך מודל שפה כותב קוד

הנחיה למתרגל AI

בשיעור זה ארצה להבין, ברמה עקרונית ובלי מתמטיקה, מהו מודל שפה ואיך הוא מייצר קוד. זה יעזור לי להבין מתי אפשר לסמוך עליו ומתי לא.
1. הסבר שמודל שפה גדול (LLM — Large Language Model, למשל המודלים שמאחורי ChatGPT, Claude ו-Gemini) הוא תוכנה שאומנה על כמות עצומה של טקסט, כולל הרבה קוד פתוח מהאינטרנט. הוא מקבל טקסט ומחזיר טקסט: בכל צעד הוא מנבא מה חלק המילה הבא הסביר ביותר, מוסיף אותו, וממשיך עד שהתשובה שלמה. בשבילו קוד הוא עוד סוג של טקסט.
2. הסבר את ההשלכה: המודל לא מריץ את הקוד בראש ולא "יודע" שהוא נכון. הוא מייצר קוד שנראה סביר, כי קוד דומה הופיע הרבה בחומר שעליו אומן. לכן משימה נפוצה (קריאת csv, ממוצע לפי קבוצה) יוצאת לרוב טוב, ומשימה נדירה או חבילה חדשה — פחות.
3. הסבר מהו חלון הקשר (context window): הזיכרון לטווח קצר של המודל. בכל פנייה הוא רואה רק כמות מוגבלת של טקסט: ההודעות בשיחה, הקבצים שצורפו, הקוד והודעות השגיאה. מה שלא נמצא בחלון — המודל לא יודע. למשל, אם לא סיפרתי שהעמודה נקראת rt ולא RT, הוא ינחש. והסבר את הצד השני: כשהחלון מלא בחומר לא רלוונטי, או כשהשיחה ארוכה מאוד, המודל עלול "לשכוח" הוראות מההתחלה או לבלבל בין פרטים. ולכן: לתת לו את מה שרלוונטי, ולפתוח שיחה חדשה למשימה חדשה.
4. הסבר מהי הזיה (hallucination): המודל ממציא בביטחון מלא משהו שלא קיים — פונקציה, ארגומנט או חבילה — כי זה "נשמע" נכון. הסבר שזו תוצאה ישירה של ניבוי טקסט סביר, ושנעסוק בה ביחידה נפרדת.
5. הסבר שהמודלים משתנים ומשתפרים כל הזמן, ושכלים שונים משתמשים במודלים שונים, אבל שלושת העקרונות האלה — ניבוי טקסט, חלון הקשר מוגבל והזיות — נשארים.
6. סכם בארבע שורות את מה שהוסבר, וכתוב ששלב הלימוד הסתיים.
הצג את השלבים האלו אחד אחד לפי הסדר. אחרי כל שלב עצור וחכה שאכתוב „המשך״. בשיעור הזה רק מסבירים: אל תשאל אותי שאלות ואל תיתן לי תרגילים — התרגול נמצא ביחידה נפרדת.

קוד 6.3מצ'אט לסוכן: Cursor

הנחיה למתרגל AI

בשיעור זה ארצה להבין את ההבדל בין שלוש דרכים לעבוד עם בינה מלאכותית בקוד, ולהכיר את Cursor, הכלי שבו נשתמש. אני עובד/ת על Windows.
1. הסבר שלוש רמות:
(א) צ'אט: אני מעתיק/ה קוד לחלון באתר, מקבל/ת תשובה ומעתיק/ה חזרה. המודל לא רואה את הקבצים שלי.
(ב) השלמה אוטומטית (copilot, "טייס משנה"): בתוך עורך הקוד, המודל מציע את המשך השורה שאני כותב/ת, ואני מאשר/ת ב-Tab.
(ג) סוכן (agent): מודל שקיבל כלים — הוא יכול לקרוא קבצים בתיקיית הפרויקט, לערוך אותם ולהריץ פקודות בטרמינל — ופועל בכמה צעדים כדי להשלים משימה. כוח גדול, ולכן גם סיכון גדול.
2. הסבר מה זה Cursor: עורך קוד שבנוי על VS Code (ולכן ייראה לי מוכר), עם סוכן מובנה. ציין במשפט אחד חלופות שעובדות על אותם עקרונות: Claude Code, סוכן שרץ בתוך הטרמינל, ו-GitHub Copilot, שפועל בתוך VS Code. הסבר שלכלים האלה יש מכסה חינמית מוגבלת, ומעבר לה הם בתשלום.
3. הסבר איך מתחילים: מורידים את Cursor מ-cursor.com/download ומתקינים; פותחים תיקיית פרויקט (File > Open Folder) — תמיד תיקייה ייעודית, לא תיקיית הבית, כי הסוכן רואה את מה שבתיקייה הפתוחה; ופותחים את חלון הסוכן בצד עם Ctrl+I. הסבר שבטרמינל המובנה אפשר לבחור Git Bash, כמו ב-VS Code (Ctrl+Shift+P ואז Terminal: Select Default Profile).
4. הסבר איך נראה שינוי שהסוכן מציע: diff — תצוגה שמראה בכל קובץ אילו שורות נמחקו (באדום) ואילו נוספו (בירוק). לכל שינוי יש כפתורים לאשר או לדחות (השמות משתנים בין גרסאות, למשל Keep ו-Undo). הסבר שהסוכן שומר גם נקודות שחזור (checkpoints), אבל הן לא תחליף ל-Git.
5. הסבר את הגדרת הבטיחות לפקודות טרמינל: ב-Settings של Cursor, תחת Run Mode, לבחור Allowlist ולהשאיר את הרשימה ריקה — כך הסוכן יבקש את אישורי לפני כל פקודה. והסבר למה: פקודה כמו rm -r מוחקת לצמיתות.
6. סכם בארבע שורות את מה שהוסבר, וכתוב ששלב הלימוד הסתיים.
הצג את השלבים האלו אחד אחד לפי הסדר. אחרי כל שלב עצור וחכה שאכתוב „המשך״. בשיעור הזה רק מסבירים: אל תשאל אותי שאלות ואל תיתן לי תרגילים — התרגול נמצא ביחידה נפרדת.

קוד 6.4לכתוב מפרט לפני שמבקשים קוד

הנחיה למתרגל AI

בשיעור זה ארצה ללמוד לכתוב מפרט קצר לפני שאני מבקש/ת מסוכן לכתוב קוד.
1. הסבר את הבעיה בהנחיה כמו "תנתח לי את הנתונים": המודל ינחש את מבנה הקובץ, את שמות העמודות ואת הכללים, וכל ניחוש הוא מקום לטעות.
2. הסבר מהו Spec-Driven Prompting ("הנחיה מונחית מפרט"): לפני שמבקשים קוד, כותבים מפרט (spec) — כמה שורות שמגדירות בדיוק מה רוצים. הסבר את חמשת חלקיו:
(א) קלט: איזה קובץ, באיזו תיקייה, ומה מייצגת כל שורה.
(ב) מבנה: שמות העמודות והסוג של כל אחת.
(ג) כללים: למשל אילו ניסויים מסננים ולמה.
(ד) פלט: מה מקבלים בסוף — טבלה, גרף או קובץ — ובאיזה שם.
(ה) אילוצים: שפה, חבילות, ומה אסור (למשל לשנות את קובץ המקור).
3. הצג מפרט לדוגמה, כפי שהייתי שומר/ת אותו בקובץ spec.txt בתיקיית הפרויקט, והסבר כל שורה:
Input: data/stroop.csv, one row per trial
Columns: id (integer), condition (congruent or incongruent), rt (milliseconds)
Rules: drop trials with rt below 200 or above 2000
Output: mean rt per participant and condition, saved as results/means.csv
Constraints: Python with pandas only; never modify data/stroop.csv
הסבר שאפשר לכתוב מפרט גם בעברית, ושהוא נשאר בפרויקט ומתעד גם בשבילי מה החלטתי.
4. הסבר איך משתמשים בו: מבקשים מהסוכן לקרוא את spec.txt, לשאול שאלות הבהרה לפני שהוא כותב קוד, ולהסביר את מה שכתב. כשמשהו משתנה — מעדכנים קודם את המפרט.
5. הסבר שמפרט טוב מתאר את הנתונים בלי לחשוף אותם: שמות עמודות ושתיים-שלוש שורות מומצאות מספיקים.
6. סכם בארבע שורות את מה שהוסבר, וכתוב ששלב הלימוד הסתיים.
הצג את השלבים האלו אחד אחד לפי הסדר. אחרי כל שלב עצור וחכה שאכתוב „המשך״. בשיעור הזה רק מסבירים: אל תשאל אותי שאלות ואל תיתן לי תרגילים — התרגול נמצא ביחידה נפרדת.

קוד 6.5צעדים קטנים

הנחיה למתרגל AI

בשיעור זה ארצה להבין למה עובדים עם סוכן בצעדים קטנים, ואיך זה נראה בניתוח של ניסוי.
1. הסבר מהו Iterative Refinement ("שיפור בצעדים"): במקום הנחיה ענקית אחת ("תטען, תנקה, תנתח ותצייר"), מבקשים צעד אחד, בודקים אותו, ורק אז ממשיכים. הסבר למה: שינוי קטן קל לקרוא ולבדוק, וכשמשהו נשבר יודעים בדיוק באיזה צעד.
2. הצג ניתוח של ניסוי סטרופ (הקובץ stroop.csv עם העמודות id, condition ו-rt) בארבעה צעדים, ולכל צעד מה בודקים לפני שממשיכים:

קוד 6.7כשהקוד נופל: traceback ושורש הבעיה

הנחיה למתרגל AI

בשיעור זה ארצה ללמוד מה עושים כשקוד שהסוכן כתב נכשל: איך קוראים את דוח השגיאה, איך מעבירים אותו לסוכן, ואיך מבקשים ממנו למצוא את הסיבה ולא רק "לתקן". הראה דוגמאות גם בפייתון וגם ב-R.
1. הסבר שכשקוד נכשל, המפרש מדפיס בטרמינל דוח שגיאה, שבפייתון נקרא traceback ("עקבות לאחור"). הראה traceback קצר שנוצר מהשורות:
import pandas as pd
df = pd.read_csv("data/stroop.csv")
print(df["RT"].mean())
והסבר איך קוראים אותו: השורה האחרונה היא סוג השגיאה וההודעה (כאן KeyError: 'RT'), והשורות שמעליה מראות איפה זה קרה — שם הקובץ ומספר השורה, מהקוד שלי ועד עומק החבילה.
2. הראה את אותה טעות ב-R:
df = read.csv("data/stroop.csv")
mean(df$RT)
והסבר שכאן R לא נעצר: df$RT מחזיר NULL, ו-mean מחזיר NA עם אזהרה (Warning). זו שגיאה "שקטה" שקל לפספס. הסבר ששגיאה של ממש ב-R מתחילה ב-Error, ושהפקודה traceback() מראה איפה היא קרתה.
3. הסבר איך מעבירים שגיאה לסוכן: מעתיקים את הדוח המלא מהטרמינל — לא "זה לא עובד" ולא רק את השורה האחרונה — ומוסיפים איזו פקודה הרצתי ומה ציפיתי שיקרה.
4. הסבר את חיפוש שורש הבעיה (root cause) ואת "ברווז הגומי": מתכנתים מסבירים בעיה בקול לברווז גומי, ותוך כדי ההסבר מבינים אותה. עם בינה מלאכותית: מתארים מה ציפיתי שיקרה ומה קרה בפועל, ומבקשים מהסוכן לנתח את הסיבה בלי לכתוב קוד חדש עד שהבנתי. הצג ניסוח לדוגמה:
I expected the mean rt per condition, but got KeyError: 'RT'. Do not change any code yet. Explain the cause in two sentences.
הסבר למה: "תיקון" בלי הבנה מוביל לטלאי על טלאי, ולפעמים מסתיר את הבעיה במקום לפתור אותה.

1. הסבר שמפתח API הוא כמו סיסמה: מי שמחזיק בו יכול להשתמש בשירות על חשבוני. הסבר את הטעות הנפוצה: לכתוב את המפתח בתוך הסקריפט, ולעשות commit ו-push. מרגע זה הוא ציבורי — גם אם מוחקים אותו אחר כך הוא נשאר בהיסטוריה של Git — ויש תוכנות שסורקות את GitHub ומחפשות מפתחות. אם זה קרה: מבטלים את המפתח באתר של השירות ומייצרים חדש.
2. הסבר מהו משתנה סביבה (environment variable): משתנה שמוגדר מחוץ לקוד, בסביבה שבה התוכנה רצה, וכל תוכנה שהופעלה ממנה יכולה לקרוא אותו. הזכר שכבר פגשתי כאלה בטרמינל: PATH ו-SHELL. הראה ב-Git Bash:

3. הסבר מהו קובץ .env: קובץ טקסט בתיקיית הפרויקט, עם שורה לכל סוד:
MY_API_KEY=abc123
הסבר שהקוד טוען ממנו את הסודות כמשתני סביבה — בפייתון עם החבילה python-dotenv, וב-R עם החבילה dotenv או הקובץ .Renviron — וקורא אותם בשם בלבד: os.getenv("MY_API_KEY") בפייתון, Sys.getenv("MY_API_KEY") ב-R. בקוד מופיע רק השם, אף פעם לא הערך.
4. הסבר את השלב הקריטי: להוסיף את השורה .env לקובץ .gitignore לפני ה-commit הראשון, ולוודא עם git status שהקובץ לא מופיע.
5. הסבר איך עובדים עם סוכן: לכתוב בקובץ ההנחיות "Load API keys only from environment variables; never write keys in code", ולא להדביק מפתח בצ'אט. הסבר ש-Cursor מסתיר מהסוכן כברירת מחדל קובצי .env וקבצים שב-.gitignore, ושאפשר להוסיף עוד בקובץ .cursorignore — אבל זו לא הגנה מלאה, כי פקודות טרמינל שהסוכן מריץ עדיין יכולות לקרוא אותם.
